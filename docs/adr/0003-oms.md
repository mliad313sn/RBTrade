# ADR 0003 — Order management, paper engine, pre-trade risk, kill switch and appropriateness

- Status: Accepted (2026-09-26)
- Deciders: S4 (trading-systems engineer, lead), S2 (senior trader), S8 (risk and compliance), S3, S9, S10, Project Owner
- Context: goal 03, the 2026-09-26 scope amendment (global coverage, appropriateness), Sponsor decision OQ-S2 (B-018), B-501, goal 02 fill-safety rules.

## Decision

### 1. One path for every order

`OmsService.submit` is the only way an order enters the system: REST (`manual`, `ai-draft-accepted`), the kill switch (`kill-switch` flatten orders) and, from goal 06, robots (`robot:{uuid}`, actor type `robot`). REST refuses `robot:*` sources until goal 06 can prove robot ownership. Each submission runs in one READ COMMITTED transaction that holds the account row lock (`SELECT … FOR UPDATE`): idempotency check, market snapshot, valuation, preview, risk, state machine, immediate matching, ledger postings, positions and a single batched audit append. Nothing inside that transaction takes a second pool connection (a 50-request burst exhausted the pool before this rule; registry lookups are stale-while-revalidate for the same reason).

### 2. Order model and state machine

- `orders.type` is what the user asked for; `exec_type` is how the engine works the row. Brackets and attached SL/TP create reduce-only children on the entry's first fill, sized to the filled quantity and linked by an `oco_group`. OCO is a container row (holding the `client_order_id`) with two legs.
- States: `new → accepted → working → partially_filled → filled | cancelled | rejected | expired`, as a table in `@kora/domain` (`ORDER_TRANSITIONS`) with an exhaustive 64-pair test. Every transition is audited as `order.<state>`; triggers (`order.triggered`) and amendments (`order.amended`) too.
- Idempotency: unique `(account_id, client_order_id)` + request hash. Same body → the original order (HTTP 200, `idempotentReplay`); different body → 409. Rejections are persisted, so a replay returns the same 422.

### 3. Paper engine

- **Fill safety (goal 02):** no fill without a quote; when the quote is flagged stale or older than the asset-class threshold; when the last feed status is missing, older than 5 s, `down`, or not `up` for the quote's source; when the symbol is in `staleSymbols`; when `sessionStatus` is not `open`; or when the FX rate to the account currency is not fresh. Orders that fill on arrival are rejected with a code; resting orders are held and fill once the market is safe.
- **Execution:** market and triggered stops walk the depth ladder (partial fills across levels; a remainder keeps working and only consumes a new depth snapshot). Slippage model per asset class (registry `asset_class_trading`): the ladder walk (spread + size vs depth), `impact_ticks` per level beyond the top, and a volatility term `vol_factor × |Δmid|` rounded up to a tick. Stops trigger on the correct side (buy stops on the ask, sell stops on the bid); a gap fills at the next available price and the fill records `reference_price` (the stop) and the adverse `slippage`. Resting limits fill as maker at their limit when the touch reaches them. IOC/FOK/DAY/GTD semantics; DAY ends at the venue's close (lunch breaks skipped; local midnight for 24/7 venues).
- **Every fill stores** `quote_at_decision` (bid, ask, seq, source, timestamps), `price`, `reference_price`, `slippage`, commission, spread cost, FX rate and conversion cost, realised P&L.

### 4. Money: base currency, margin-traded, double-entry

- One base currency per paper account (default USD, changeable before any activity). Every instrument is margin-traded (P&L-settled): opening a position moves no cash. Realised P&L, commission, swaps and FX conversion are booked in base currency at the fill-time rate.
- Quantity semantics come from the registry: `multiplier_mode` `unit` (FX, metals, crypto, equities, ETFs, funds, CFDs, indices), `contract` (futures, options, energy, agri: multiplier = `contract_size`) or `percent_of_par` (bonds). This matches the prototype (EUR/USD 100,000 units, XAU/USD in ounces) and the registry qty grids; no asset class is special-cased in code.
- FX: direct, inverse or USD-triangulated mid from live SIMULATED FX quotes; five SIMULATED pairs were added (USDHKD, USDCNY, USDINR, USDZAR, USDBRL) so every seeded quote currency converts. Conversion fee = fee schedule `fx_conversion_bps`, shown in the preview.
- Ledger: journals + entries, positive = debit, amounts quantised to 10 decimals so sums are exact in the 40-digit working precision (a fast-check run found an unbalanced journal before this rule). The database refuses unbalanced journals (deferred constraint trigger) and any UPDATE/DELETE on ledger and fills (trigger, even for the owner; privileges revoked for `kora_app`). `accounts.cash` is a cache checked by reconciliation.
- Registry-driven placeholders: `fee_schedules` (FK from `instruments.fee_schedule_id`), `asset_class_trading`, `instruments.margin_rates[tier]`. All flagged `simulated` (OQ-M1, OQ-M5).

### 5. Pre-trade risk

`evaluateRisk` is pure and synchronous (p95 0.14 ms for the rules; 4.9 ms p95 including loading the context from Postgres and Redis). Codes: `MAX_ORDER_NOTIONAL, FAT_FINGER, MAX_POSITION, MAX_LEVERAGE, INSUFFICIENT_MARGIN, DAILY_LOSS_LIMIT, WEEKLY_LOSS_LIMIT, ORDER_RATE_LIMIT, SESSION_CLOSED, INSTRUMENT_NOT_TRADABLE, NO_MARKET_DATA, MARKET_DATA_STALE, FEED_NOT_OK, FX_RATE_UNAVAILABLE, NOVICE_ORDER_TYPE, NOVICE_STOP_REQUIRED, NOVICE_LEVERAGE, REDUCE_ONLY_WOULD_INCREASE, POST_ONLY_WOULD_TAKE, STOP_LOSS_WRONG_SIDE, TAKE_PROFIT_WRONG_SIDE, TRADING_HALTED, FOK_INSUFFICIENT_DEPTH`, each with a plain-language message. Orders that reduce a position (including oversize reduce-only orders, clipped at fill) are exempt from exposure and loss-limit rules, so a user can always get out. Novice guardrails apply to novice-only accounts and to anyone in the Novice view. Platform limits come from env (SIMULATED placeholders, OQ-R5); an account can tighten but never loosen them. Loss limits compare equity with the first valuation of the UTC day/ISO week.

### 6. Kill switch

Same REST contract as goal 01 plus an optional `reason`. One transaction: halt flag (`trading_halted`, scope never narrows), `kill_switch.requested` and `kill_switch.robots_halted`, one `UPDATE … RETURNING` cancelling every open order, a reduce-only market flatten order per position through the normal engine path, `kill_switch.completed`; all child events share a `killSwitchId` and are appended with `AuditService.recordMany` (one chain lock, one insert). 1,000 open orders + 4 positions complete in ~0.2 s end to end, so B-006 (per-partition chains) is not needed yet. If the market is unsafe, flatten orders stay working and fill when it recovers (`flattenPending`). Resume (`POST /kill-switch/resume {reason}`) needs trader/quant/risk_officer/admin with MFA; risk officers and admins can resume another account. A `kora:ctl:robots` Redis message announces halts/resumes to the bot runner.

### 7. Reconciliation and LIVE

Every 60 s and on demand, per account in a REPEATABLE READ snapshot: engine positions vs an independent replay of the fills (`PaperBrokerAdapter`), `accounts.cash` vs the ledger, ledger total = 0. Mismatch → critical `alerts` row, `reconciliation.mismatch` audit event, error log. `BrokerExecutionAdapter` + `LiveBrokerStub` (refuses unless `LIVE_TRADING_ENABLED`, which config already refuses, **and** an active `compliance_signoffs` row, which `kora_app` cannot write; then still refuses for lack of a licensed broker). A trigger refuses LIVE accounts without a sign-off.

### 8. Real time

Private channels `orders:{account}`, `positions:{account}`, `account:{account}` on the goal 02 bus and gateway; the gateway checks ownership (risk officers/admins may read any). Order events are batched per transaction and never conflated; positions/account snapshots are coalesced per account (50 ms). The web polls REST as well, so it works without the socket.

### 9. Appropriateness and the questionnaire engine (B-018)

Sign-up creates `novice` only. Questionnaires are versioned JSON data files (`apps/api/src/appropriateness/questionnaires/`), validated by `QuestionnaireDefinitionSchema`, published to `questionnaires` at boot with a checksum; editing a published version fails the boot and a trigger blocks UPDATE/DELETE. Options carry points (right/wrong = 1/0; profiles use weights), so goal 08 knowledge checks and goal 09 suitability reuse the engine (`kind`). Grading is server-side; attempts store version, score, pass mark and outcome, never answers. A fail starts a cool-down; a pass grants `trader`, switches the default view to Pro, clears the session cookie, and the next login forces TOTP enrolment. Pass mark 75 % and cool-down 24 h are data (env-overridable) and the questions are SIMULATED placeholders pending Compliance (OQ-C1).

## Consequences

- Goals 04, 06 and 08 build on `POST /orders/preview` + `POST /orders` and the private channels; robots use `OmsService.submit` with `actor.type = 'robot'`.
- Single api writer per account; horizontal scale-out of the matching loop needs a leader or per-account sharding (B-302).
- Paper realism limits are documented (no queue position, no trade-print matching, swaps ×1 every day) (B-304).
- Users cannot read engine (system-actor) audit events about their own orders through `/audit` yet (B-303).
